01 class vs object

The stamp and the prints

Say this

"A class is the stamp. An object is a print it makes. One stamp, many prints — and changing one print never touches the others."

# the stamp — no dog exists yet class Dog: def __init__(self, name): self.name = name # the prints — now dogs exist rex = Dog("Rex") bella = Dog("Bella") print(rex.name, bella.name) # Rex Bella
Q · the interviewer asks

"What's the difference between a class and an object?"

"A class is the blueprint or template; an object is an instance built from it. The class is written once and costs no memory for data; each object gets its own memory for its own attribute values."

"How many objects can one class make?"

Any number. That is the entire point of the stamp.

02 self · __init__

The hidden first seat

This is the one that makes people freeze. self is not a keyword and it is not magic — it is just the first parameter, and Python fills it in for you.

Say this

"Every method has a hidden first seat. When I write acc.deposit(50), Python quietly runs BankAccount.deposit(acc, 50) — the object sits in seat one. That seat is called self."

class BankAccount: def __init__(self, owner, balance=0): # runs at birth self.owner = owner self.balance = balance def deposit(self, amount): if amount <= 0: raise ValueError("deposit must be positive") self.balance += amount return self.balance acc = BankAccount("amaan", 100) acc.deposit(50) print(acc.balance) # 150
Q · the interviewer asks

"What is self?"

"The instance the method was called on. Python passes it automatically as the first argument, so acc.deposit(50) is really BankAccount.deposit(acc, 50)."

"Is self a keyword?"

No — it's a naming convention. You could call it anything and the code would run. Don't, though: every Python programmer alive reads self.

"What is __init__? Is it a constructor?"

It's the initialiser — it runs on an object that already exists and fills in its starting attributes. Strictly, __new__ creates the object and __init__ sets it up. Saying "constructor" is accepted, but knowing the distinction is a bonus mark.

03 class vs instance attributes · the trap

One whiteboard, or a notebook each

You have met this bug before, wearing a different hat — it is the mutable default argument problem. Third time you've seen this shape. It will be the last.

Say this

"A class attribute is one whiteboard on the wall — everybody writes on the same one. An instance attribute is a notebook each. Mutable things belong in __init__, or every object shares them."

# BROKEN — one list, shared by every Cart class CartBad: items = [] # class attribute — the whiteboard def add(self, x): self.items.append(x) a, b = CartBad(), CartBad() a.add("apple") print(b.items) # ['apple'] ← b was never touched # FIXED — a fresh list per instance class Cart: def __init__(self): self.items = [] # instance attribute — a notebook each def add(self, x): self.items.append(x) c, d = Cart(), Cart() c.add("apple") print(d.items) # [] ← correct
Q · the interviewer asks

"Difference between a class attribute and an instance attribute?"

"A class attribute is shared by every instance; an instance attribute belongs to one object and is set in __init__. Mutable class attributes are a classic bug — it's the same trap as a mutable default argument."

"So class attributes are always bad?"

No — they're right for things genuinely shared: a constant like species = "dog", or a counter of how many objects have been created. The danger is only with mutable ones (lists, dicts, sets).

"What does a.items = ['x'] do — change the whiteboard?"

No, and this catches people. Assigning creates a new instance attribute that shadows the class one, for a only. Mutating (a.items.append) reaches through to the shared list. Assignment writes a new notebook; mutation edits the whiteboard.

04 inheritance · super()

The staircase

Say this

"super().__init__() means 'first, go upstairs and run the parent's setup'. Then come back down and add your own. Skip it and the parent's attributes never exist."

class SavingsAccount(BankAccount): def __init__(self, owner, balance=0, rate=0.05): super().__init__(owner, balance) # upstairs self.rate = rate # back down def add_interest(self): self.balance += self.balance * self.rate return self.balance s = SavingsAccount("amaan", 1000) print(s.add_interest()) # 1050.0 print(s.owner) # amaan ← free from the parent
Q · the interviewer asks

"Why call super().__init__()?"

"Because the child's __init__ replaces the parent's, it doesn't add to it. Without the call, owner and balance are never set — you get an AttributeError much later, far from the real cause."

"Does super() mean 'the parent'?"

Close, and the better answer is: the next class in the MRO (method resolution order). With single inheritance that is the parent. With multiple inheritance it may not be — which is exactly why super() beats hard-coding Parent.__init__(self, ...).

"What is method overriding?"

Defining a method in the child with the same name as one in the parent. The child's version wins. It's runtime polymorphism, and Python supports it fully.

05 the five types of inheritance

Five family shapes

When they say "what are the types of inheritance?" this is the list they want, and they want it fast. Don't memorise words — memorise the five shapes. Step through and draw each one in the air.

Say this — the five, in order

"Single — one parent, one child. Multiple — two parents, one child. Multilevel — grandparent, parent, child. Hierarchical — one parent, many children. Hybrid — a mix, usually the diamond, resolved by the MRO."

# hybrid / diamond — and the answer to "which who() runs?" class A: def who(self): return "A" class B(A): def who(self): return "B" class C(A): def who(self): return "C" class D(B, C): pass print(D().who()) # B ← left to right print([k.__name__ for k in D.__mro__]) # ['D', 'B', 'C', 'A', 'object']
Q · the interviewer asks

"What is the diamond problem, and how does Python solve it?"

"D inherits from B and C, which both inherit from A — so which who() runs? Python resolves it with the MRO, computed by the C3 linearisation algorithm, left to right, and each class appears once. You can print it with D.__mro__."

"Does Python support multiple inheritance?"

Yes — unlike Java, which allows it only for interfaces. Python allows it for real classes and handles the conflicts with the MRO.

"Is inheritance always the right tool?"

No — prefer composition. Use inheritance for is-a (a SavingsAccount is a BankAccount) and composition for has-a (a Car has an Engine). Deep hierarchies get rigid fast.

06 polymorphism · duck typing

The universal remote

Say this

"One button, different machines. I call the same method name and each object does its own thing. In Python I don't even need a shared parent class — if it has the method, it works. That's duck typing."

class Dog: def speak(self): return "Woof" class Robot: def speak(self): return "Beep" class Cat: def speak(self): return "Meow" for thing in (Dog(), Robot(), Cat()): print(thing.speak()) # Woof / Beep / Meow — no shared parent anywhere
Q · the interviewer asks

"Do you need inheritance for polymorphism in Python?"

"No." Say it flatly — most candidates say yes. "Python uses duck typing: if it walks like a duck and quacks like a duck, it's a duck. The method just has to exist."

"Types of polymorphism?"

Compile-time (method overloading) and run-time (method overriding). Then the Python twist below — which is where you win the point.

07 overloading vs overriding · the trick question

The card that covers the card

Asked constantly, and it's a trap if you learned OOP from Java or C++. Python's answer is different, and knowing that is the whole point of the question.

Say this

"Python does not support true method overloading — a second definition with the same name simply replaces the first. I get the same effect with default arguments or *args. Overriding is different and does work: that's a child class redefining a parent's method."

# overloading — does NOT work in Python class Calc: def add(self, a, b): return a + b def add(self, a, b, c): return a + b + c # this one wins Calc().add(1, 2) # TypeError: Calc.add() missing 1 required positional argument: 'c' # the Pythonic way to get the same effect class Calc2: def add(self, *args): return sum(args) print(Calc2().add(1, 2), Calc2().add(1, 2, 3)) # 3 6
Q · the interviewer asks

"Overloading vs overriding?"

"Overloading — same method name, different parameters, resolved at compile time. Overriding — a child redefining a parent's method, resolved at run time. And in Python, overloading isn't supported: the later definition just replaces the earlier one. I'd use *args, default arguments, or functools.singledispatch instead."

"Why doesn't Python support it?"

Because a class body is just a namespace — def binds a name, so the second def add overwrites the first exactly like x = 1; x = 2. Python is dynamically typed, so there are no parameter types to dispatch on.

08 encapsulation · abstraction

The vending machine

These two get confused more than any other pair, because they're both about "hiding". One image separates them for good: the glass and the buttons.

Say this

"Encapsulation is the glass — the data is locked inside and you can only reach it through methods. Abstraction is the button panel — a simple surface that hides how complicated the inside is. Encapsulation hides data; abstraction hides complexity."

class Acct: def __init__(self): self._soft = "convention only" # one _ : please don't touch self.__hard = "name mangled" # two _ : renamed by Python a = Acct() a._soft # works fine — nothing stops you a.__hard # AttributeError: 'Acct' object has no attribute '__hard' a._Acct__hard # 'name mangled' ← still reachable!
Q · the interviewer asks

"Difference between encapsulation and abstraction?"

"Encapsulation is bundling data with the methods that guard it — implementation-level. Abstraction is exposing only what matters and hiding the how — design-level. Encapsulation is how you achieve abstraction."

"Is anything in Python truly private?"

No — and say so confidently. "A single underscore is a convention. A double underscore triggers name mangling to _ClassName__attr, which prevents accidental clashes in subclasses but doesn't stop anyone determined. Python's philosophy is we're all consenting adults here."

"How do you achieve abstraction in Python?"

With the abc module: inherit ABC and mark methods @abstractmethod. Instantiating the abstract class then raises TypeError: Can't instantiate abstract class Shape with abstract method area — it forces subclasses to honour the contract.

09 the four pillars

The list they always ask for

"What are the four pillars of OOP?" is the single most-asked OOP question there is. Here they are, each welded to a picture you've already stepped through.

Encapsulation🔒 the glass

Bundle the data with the methods that guard it. _balance is inside; deposit() is the way in.

Abstraction🎛 the buttons

Show a simple surface, hide the machinery. You press withdraw() and never hear about the ledger.

Inheritance🪜 the staircase

A child reuses and specialises a parent. SavingsAccount gets everything BankAccount has, plus interest.

Polymorphism📺 the remote

One call, many behaviours. .speak() on Dog, Robot and Cat — no shared parent needed.

Say this — in one breath

"Encapsulation, abstraction, inheritance, polymorphism. Glass, buttons, staircase, remote."

Q · the follow-up that separates people

"Give me an example from your own code."

Have one ready and reuse it every time. From a task tracker: Encapsulation — the Task class guards its own status through a method instead of letting anything set it. Abstraction — task.complete() hides the timestamping and saving. Inheritance — RecurringTask(Task) adds a schedule. Polymorphism — every task type implements summary() its own way and the list page calls one method for all of them.

10 @property · @classmethod · @staticmethod

The wall that's really a door

Say this

"@property makes a method look like an attribute. You read c.area with no brackets, but a function runs behind the wall. It's how you add validation or make something read-only without changing the code that uses it."

class Circle: def __init__(self, radius): self._radius = radius @property def area(self): return 3.14159 * self._radius ** 2 c = Circle(2) print(c.area) # 12.56636 — no brackets c.area = 99 # AttributeError — read-only for free

And the decorator question they ask right after — the difference is what arrives in the first seat.

regular methodFirst seat: selfNeeds the specific object. Most methods.
@classmethodFirst seat: cls (the class itself)Can build new objects → alternative constructors. Temp.from_fahrenheit(212) returns a new Temp.
@staticmethodFirst seat: nothingTouches neither the object nor the class — it just lives here because it belongs here. A noticeboard on the factory wall.
class Temp: def __init__(self, celsius): self.celsius = celsius @classmethod def from_fahrenheit(cls, f): # gets the CLASS → can build return cls((f - 32) * 5 / 9) @staticmethod def is_freezing(c): # gets NOTHING return c <= 0 print(Temp.from_fahrenheit(212).celsius) # 100.0 print(Temp.is_freezing(-5)) # True
Q · the interviewer asks

"@classmethod vs @staticmethod?"

"A classmethod receives the class as cls, so it can create instances — that's why it's used for alternative constructors. A staticmethod receives nothing; it's a plain function grouped inside the class for organisation."

"Why use @property instead of a plain attribute?"

To add validation, computation or read-only access later without breaking callers. Code that already says c.area keeps working — you changed the inside, not the interface. That's encapsulation in one decorator.

11 the blank page

What to type first, every time

Same idea as the five moves for functions. A class is always these five, in this order — and the first four don't need a single clever thought, because the question already told you what the thing is and what it holds.

Say this while you type

"Name, Birth, State, Show, Do. I'll set the shape up first — it takes an owner and a balance, so that's __init__; a __repr__ so I can debug it; then the behaviour."

Q · the interviewer asks

"__str__ vs __repr__?"

"__str__ is for users — what print() shows. __repr__ is for developers — what the shell and the debugger show, and what appears when the object is inside a list. If I only write one, I write __repr__, because str() falls back to it."

"You've gone quiet — what are you thinking?"

Never go quiet. Narrate the skeleton: "Setting up the shape first — it's a noun, so a class; it needs a name and a balance to exist, so those go in __init__." You've said something true and bought ten seconds.
