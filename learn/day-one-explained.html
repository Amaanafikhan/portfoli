The four things
that actually bite.

Day 1 has about thirty facts in it. Four of them cause almost every bug you'll write this month, and they're all the same kind of misunderstanding: something you thought was a copy turns out to be a shortcut to the original. This page explains those four properly, then covers the rest quickly.

01 Environment

Why your imports break in a new terminal

A virtual environment is a folder containing its own Python and its own packages. Without one, every project on your machine shares a single set — so two projects that need different versions of the same library cannot both work.

No venv
project-a needs requests 2.28
project-b needs requests 2.32
↓   ↓
one global site-packages
only one version fits
With venv
project-a venv/ → 2.28
project-b venv/ → 2.32
↓   ↓
separate folders
both projects work

The ninety-percent bug

Activation is per terminal session. Open a new tab, and you are outside the venv again — even though the folder still exists and you never closed the project. Nine out of ten ModuleNotFoundErrors are this. The (venv) prefix on your prompt is the only thing that proves you're inside.

pip freeze writes everything installed, including sub-dependencies you never asked for. That's correct — those are real requirements of your real requirements. And the reason a Dockerfile installs requirements before copying your code: dependencies change rarely, code changes constantly, so the slow step goes first and stays cached.

02 The big one

A name is a label, not a box

This is the single most useful idea on this page. In Python, variables don't contain values — they're name tags stuck onto objects that live somewhere in memory. b = a sticks a second tag on the same object. It has never once made a copy.

How to tell them apart

== asks are these equal?  is asks are these the same object? Two separate lists holding the same numbers are == but not is. That's the whole distinction, and it's why x is None is the correct way to check for None — there is only ever one None object.

Shallow versus deep

.copy() duplicates the outer container but not what's inside it. If your list holds dictionaries, a copy gives you a new list pointing at the same dictionaries — edit one and both lists see it. copy.deepcopy() copies all the way down. Reach for it only when you need it; it's slower and it can't copy everything.

Immutable objects — int, float, str, bool, tuple — sidestep this entirely. You can't change them in place, so sharing a tag is harmless. That's also why they're safe as dict keys, and why list, dict and set are not.

03 Slicing

Why the stop is excluded

Everyone trips on [start:stop:step] once, because the stop is left out. It isn't arbitrary — think of the numbers as sitting between the items, like fence posts. Then a slice is just "from post 1 to post 4," and the arithmetic always works out.

The payoff

nums[:3] and nums[3:] split the list with no overlap and no gap — every item appears exactly once, and the length of nums[a:b] is simply b - a. Neither would be true if the stop were included. It also means an empty slice like nums[2:2] is well-defined rather than an error.

All of it works identically on strings, since a string is a sequence of characters. name[::-1] reverses it, name[:1] is the first letter as a string.

04 Comprehensions

Three slots, always in the same order

A comprehension is a loop that builds a new collection, written as one expression. Once you see it as three fixed slots, you can read any of them at a glance — and write them without thinking.

Read it in this order

What I want → where it comes from → which ones qualify. [n * n (what) for n in nums (where) if n % 2 == 0] (which). It always builds something new; the original is never touched.

When to write the loop instead

The moment you need a try/except — comprehensions can't hold one. Or when there's more than one condition and a transformation. Or any nesting past two levels. A comprehension nobody can read is worse than four clear lines, and you are one of the people who won't be able to read it in March.

05 Unpacking & f-strings

Two shorthands worth real memory

Unpacking assigns several names at once from a sequence. The starred form catches "everything else," and the double-star form merges dictionaries — which is how nearly every real application layers its configuration.

The config pattern

{**defaults, **from_file, **from_env} — on a key conflict the rightmost wins, so each layer overrides the one before it. Defaults first, most specific last. That single line replaces a page of if-statements.

And f-strings: they embed expressions directly, they're the fastest option, and f"{value=}" prints both the name and the value at once — the quickest debugging tool Python has.

06 Functions

Parameters, arguments, and readable calls

Parameters are the names in the definition. Arguments are the values you pass. Positional arguments are matched by order; keyword arguments by name — and once you use a keyword, everything after it must be a keyword too.

The habit worth forming

Use keyword arguments for anything not obvious at the call site. create_task("Fix bug", True, False) is unreadable in six months; create_task("Fix bug", urgent=True, archived=False) explains itself and survives someone reordering the parameters.

*args collects leftover positional arguments into a tuple; **kwargs collects leftover keyword arguments into a dict. The asterisks are the syntax — the names are only convention. Both also work in reverse, to spread a collection back into a call.

07 The famous one

The mutable default argument

Default values are evaluated once, when the function is defined — not each time it's called. So a default list is created a single time and shared by every call, forever. Press the button on the left a few times and watch it happen.

✗ tags=[]
def add_tag(tag, tags=[]):
    tags.append(tag)
    return tags
✓ tags=None
def add_tag(tag, tags=None):
    if tags is None:
        tags = []
    tags.append(tag)
    return tags

What it looks like in the wild

"Why is data from a previous request appearing in this one?" The list isn't leaking between users because of threading or caching — it's the same list object every call has been appending to since the process started. Restarting the program appears to fix it, which sends you looking in exactly the wrong place.

The rule, with no exceptions

Never use a list, dict or set as a default value. Default to None and build it inside the function. Immutable defaults — numbers, strings, True, None, tuples — are always safe, because there's nothing to accumulate.

08 Scope & return

Where names live, and what comes back

Python resolves a name by looking outward through four layers: Local, then Enclosing, then Global, then Built-in. It stops at the first match. A name created inside a function dies when the function ends.

The silent None

A function with no explicit return returns None. So result = my_list.sort() gives you None, not a sorted list — .sort() sorts in place. Decide deliberately for every function you write: does it mutate its input, or return a new value? Doing both is confusing. Doing neither is a bug.

This is also the real cause of most AttributeError: 'NoneType' object has no attribute ... messages. Don't debug where it broke — trace back to whatever handed you the None.

09 Errors

Python takes the first match

Except clauses are checked top to bottom, and the first one that matches wins. Since Exception matches almost everything, putting it first makes every clause below it unreachable. Flip the toggle and raise an error to see it.

Never swallow

A bare except: or except Exception: pass catches your own typos exactly like it catches a network timeout — a NameError vanishes silently and a five-minute fix becomes a three-hour hunt. If you must catch broadly: log it, then re-raise.

The seven you'll actually meet

ValueErrorRight type, wrong value — int("abc")
TypeErrorWrong type entirely — "a" + 1
KeyErrorDict key missing — use .get() to avoid it
IndexErrorList index out of range
AttributeErrorNo such attribute — nearly always a None from upstream
FileNotFoundErrorMissing file, or the path is relative to somewhere you didn't expect
ZeroDivisionErrorDivision by zero

Raise them yourself

raise ValueError(f"Invalid priority: {priority}") at the top of a function. Failing loudly at the boundary beats bad data flowing three layers deeper, where the eventual error points at somewhere completely innocent.

else runs only when no exception was raised. finally runs always — even if you return or re-raise — which is exactly why cleanup belongs there.

10 Files & JSON

What with is really for

with guarantees cleanup on the way out of the block — whether you fall off the end, return early, or raise. Without it, a crash mid-function leaves the file handle open, and enough of those exhaust your operating system's limits.

The s is for string

load and dump work with file objects. loads and dumps work with strings. So a response body you got back over the network is json.loads, and a file on disk is json.load. Mixing them up is a rite of passage; the error message is unhelpfully vague.

Mode "w" truncates on open

Not on write — on open. open("data.json", "w") empties the file the instant that line runs, before you've written anything. If the program then crashes, the file is simply gone. Use "a" to append, and write to a temporary file first when the data matters.

The whole day, compressed
