Four boxes.
That's the whole thing.

Python gives you four ways to hold more than one thing. Every one of them is a box with a different rule about what's allowed inside. Learn the rule and you never have to memorise the table again — you just ask what the box is for.

00 The thirty-second version

Each box has one job

list

A row of things you can rearrange.

Your shopping list — cross things off, add more.

tuple

A row of things nobody can rearrange.

Your date of birth — three numbers, permanently.

dict

Labelled drawers. You open one by its label.

A contacts app — a name gets you a number.

set

A bag that refuses duplicates and has no order.

A guest list — you're on it or you're not.

Everything below is just those four sentences, slowed down. Press the buttons — every panel has a real console you can poke.

01 The default box

list

[1, 2, 3]

An ordered row of things you expect to change. When you're not sure what to use, this is the right guess about 70% of the time.

orderedchangeableduplicates okcan't be a dict key

Position is the address. cart[0] is the first thing, cart[-1] is the last. The list remembers the order you put things in, and you can change any of it whenever you like.

The trap

Searching a list means checking every item one at a time. Fine for 10 things. A disaster for 10,000 things checked in a loop — that's section 05.

02 The locked box

tuple

(1, 2, 3)

A list that has been welded shut. Same ordering, same indexing — but nothing can be added, removed, or replaced, ever.

orderedfrozenduplicates okcan be a dict key

Two reasons to reach for it. First, to say out loud that a group of values belongs together and shouldn't change — a coordinate, an RGB colour, a database row. Second, the practical one: only frozen things can be dict keys or set members, so a tuple can be a key and a list can't.

The trap

A tuple freezes which objects it holds, not the objects themselves. If there's a list inside, that list can still be changed — and the tuple can no longer be a dict key, because one of its contents isn't frozen. Press the last two buttons above; that pair catches nearly everyone.

03 The labelled drawers

dict

{"key": "value"}

Pairs. You hand it a key, it hands back a value — instantly, no matter how many pairs are in there.

keeps insertion orderchangeableno duplicate keysinstant lookup

The word that gives it away is "by." A price by product, a user by id, a count by word. The moment you hear "by," you want a dict. And if you find yourself writing data[2] while trying to remember what slot 2 meant — you wanted a dict.

The trap

d["missing"] crashes with a KeyError. Use d.get("missing") to get None instead, or d.get("missing", 0) for a default. In real code you'll use .get() far more often than square brackets.

04 The bouncer

set

{1, 2, 3}

A bag with two rules: no duplicates, and no order. In exchange it answers "is this in here?" instantly, forever, at any size.

no orderchangeableno duplicatesinstant in

Two jobs, both worth memorising. Killing duplicates in one line, and answering membership questions fast. It also does the maths you'd otherwise write loops for: a & b is what's in both, a | b is everything, a - b is what's only in the first.

The trap

No order means no s[0] — there is no "first" item to ask for. And whatever goes in must be frozen, so a set of lists is impossible. A set of tuples is fine.

05 The one that costs money

Why a set is fast and a list isn't

This is the single most common performance mistake in Python, and it's easier to see than to explain. Both boxes below hold the same 40 names. Watch what each one does to find "zoe".

a listchecks every box in order

not started

a setcomputes where it must be, goes straight there

not started

A set runs the name through a hash function, which produces the address to look at. It doesn't search — it calculates. That's why the size of the box doesn't matter to it, and why it matters enormously to a list.

Now scale it up. With 10,000 names checked 10,000 times, the list does up to 100 million comparisons and the set does about 10,000. Same output, same code shape, one word different. If something in your program is mysteriously slow, look for in or .index() inside a loop before you look anywhere else.

But don't overcorrect

Building a set costs one full pass through the data. If you're only checking membership once, converting a list to a set first is wasted work — you did the whole scan anyway. Sets pay off when you check repeatedly.

06 The only thing to memorise

Three questions, in this order

Ask them top to bottom and stop at the first "yes." This replaces the whole comparison table.

1

Am I looking things up by a name, id, or key?

Prices by product, settings by name, counts by word, anything cached by its address.

then dict

2

Do I only care whether something is in there — and never about duplicates or order?

Seen it already? Is this tag applied? Which items are in both groups? Strip the repeats.

then set

3

Order matters. Will this ever change after I build it?

If yes, it's the ordinary changeable sequence. If no — it's a fixed group, or you need it as a dict key.

changes → list   frozen → tuple

One extra rule that explains half the errors you'll hit: dict keys and set members must be frozen. Numbers, strings and tuples are frozen. Lists, dicts and sets are not. That's the entire reason {[1,2]: "x"} fails and {(1,2): "x"} works.
